# visualization_example — 웹 교보재

눌러 가며 확인하는 작은 웹 데모 **두 장**이다.

| 경로 | 무엇을 |
|---|---|
| `/` | **행렬 곱** — A 의 어느 행과 B 의 어느 열이 C 의 어느 칸을 만드는가 |
| `/schedule` | **조기 종단 스케줄** — 종단이 언제 실제 절감이 되는가 (`src/schedule.py`) |

> 교보재다. **코어 시뮬레이터는 이 패키지를 임포트하지 않는다.**
> 지워도 `run_paper_experiments.py` 는 그대로 돈다.
> (방향은 반대다 — `/schedule` 페이지가 `src.schedule` 을 **가져다 쓴다.**)

```bash
python -m utils.visualization_example
```

브라우저가 자동으로 열린다. 끄려면 `Ctrl+C`.

```bash
python -m utils.visualization_example --port 8123 --no-browser --quiet
```

| 옵션 | |
|---|---|
| `--host` | 바인딩 주소 (기본 `127.0.0.1` — 밖으로 열지 않는다) |
| `--port` | 포트 (기본 `8000`) |
| `--no-browser` | 브라우저를 자동으로 열지 않는다 |
| `--quiet` | 접속 로그를 끈다 |

## 왜 웹 프레임워크를 안 썼나

`requirements.txt` 는 **numpy 하나만 필수**로 두고 나머지는 "없어도 코어가
돌아가는" 선택 의존성으로 관리한다. 교보재 하나 때문에 Flask·FastAPI 를
필수 목록에 올릴 이유가 없어서, 표준 라이브러리 `http.server` 로 만들었다.
**추가로 설치할 것이 없다.**

numpy 조차 없어도 동작한다 — 곱셈은 순수 파이썬 삼중 루프가 하고, numpy 가
있으면 그 결과를 `A @ B` 와 대조하는 데만 쓴다. 화면 상단의 `계산 백엔드`
표시가 지금 어느 쪽인지 알려 준다.

## 파일

```
matmul.py          행렬 곱 — 곱셈 · 항별 분해 · numpy 교차 검증
schedule_demo.py   스케줄 — read_live 를 만들어 src.schedule.apply() 에 넣는다
server.py          http.server 기반 웹 서버 + JSON API
__main__.py        python -m 진입점
static/
  index.html  app.js       /         행렬 곱
  schedule.html  schedule.js  schedule.css   /schedule
  style.css        공용 3색 팔레트
```

### ★ 산술은 파이썬만 한다

`app.js` 는 곱셈도 덧셈도 하지 않는다. 브라우저가 A·B 를 들고 있다가 통째로
보내면, 서버가 C 와 항별 분해를 계산해 돌려주고, 브라우저는 그걸 그리기만 한다.

두 곳에서 따로 계산하면 **둘이 조용히 갈라져도 아무도 모른다.** 화면에 뜨는
숫자가 파이썬이 실제로 계산한 값이라는 보장이 이 데모의 전부라서, 그 보장을
지키려고 한 번 더 왕복한다. 로컬호스트라 체감 지연은 없다.

한 걸음 더 나가서 `matmul.py` 는 **매 요청마다** 수동 삼중 루프의 결과를
numpy 의 `A @ B` 와 대조한다. 어긋나면 400/500 으로 떨어지지, 틀린 그림을
그리지 않는다.

### API

상태를 서버에 남기지 않는다. 여러 명이 동시에 열어도 서로 간섭하지 않는다.

| | |
|---|---|
| `GET /api/health` | `{"ok": true, "backend": "numpy"}` |
| `POST /api/random` | `{m, n, p, seed?}` → `{A, B, C, dims, cell, backend}` |
| `POST /api/compute` | `{A, B, i?, j?}` → 같은 모양. `i`·`j` 가 있으면 `cell` 에 분해가 담긴다 |
| `POST /api/schedule` | `{n_tokens, n_planes, survival, clustering, lanes, word_tokens, batch_size, two_phase_split, compaction_cost_cycles}` → 네 정책 결과 + 평면별 내역 |

```jsonc
"cell": {
  "i": 1, "j": 2,
  "row": [1, 4, -6, 8],        // A 의 i 행
  "col": [-1, 3, 7, 2],        // B 의 j 열
  "terms": [
    {"k": 0, "a": 1,  "b": -1, "prod":  -1, "cumsum":  -1},
    {"k": 1, "a": 4,  "b":  3, "prod":  12, "cumsum":  11},
    {"k": 2, "a": -6, "b":  7, "prod": -42, "cumsum": -31},
    {"k": 3, "a": 8,  "b":  2, "prod":  16, "cumsum": -15}
  ],
  "total": -15,
  "cross_checked": true
}
```

`cumsum` 은 누산기가 k 단계까지 들고 있는 값이다. 내적이 한 번에 나오는 값이
아니라 **순차 누산**이라는 것을 보이려고 넣었다.

## 화면 읽는 법

```
[ A  5×4 ]  ·  [ B  4×3 ]  =  [ C  5×3 ]
```

색은 셋뿐이고 각각 뜻이 있다. 장식으로 쓰는 색은 없다.

| | |
|---|---|
| 주황 | A 의 **i** 번째 행 |
| 청록 | B 의 **j** 번째 열 |
| 보라 | 둘이 만드는 **C[i][j]** 와 짝지어진 **k** |

**연결 레일** — 고른 행은 아래로 우회해서, 고른 열은 위로 우회해서 C 로 들어간다.
B 를 가로지르지 않게 돌린 것이라, 두 화살표가 도착하는 곳이 곧 보라색 칸이다.

**인덱스 거터** — 여기가 핵심이다.

| | 행 | 열 |
|---|---|---|
| A | `i` | `k` |
| B | `k` | `j` |
| C | `i` | `j` |

**A 의 열 번호와 B 의 행 번호가 같은 `k`** 다. 그래서 두 행렬을 곱할 수 있다.
`k` 를 고르면 A 의 열 헤더와 B 의 행 헤더가 동시에 보라색이 되어, 두 행렬을
묶는 축이 눈에 보인다. 번호를 눌러 행·열을 통째로 고를 수도 있다.

**계산판** — 고른 행과 열을 벡터 두 개로 뽑아 세로로 맞춰 놓았다.
「항별로 재생」을 누르면 `k` 가 하나씩 진행하며 **누적** 줄이 자란다.

## `/schedule` — 조기 종단 스케줄

`src/schedule.py` 가 하는 일을 눌러 보는 페이지다. **스케줄을 다시 구현하지
않는다** — `schedule_demo.py` 는 `read_live` 를 만들어 넣고 실제
`src.schedule.apply()` 를 네 정책 모두에 대해 부른다
(`test_run_calls_the_real_schedule_module` 이 monkeypatch 로 호출을 감시한다).

### ★ 실행 타임라인 — 사이클 × 레인

이 페이지의 주인공이다. 문서의 첫 문장이 *"파이프라인에 빈 구간이 생긴다"* 이므로,
**그 빈 구간을 실제 칸으로 그린다.** 가로가 레인, 세로가 사이클이다.

```
평면 b5   cyc 0  [ 0][ 1][ 2][ 3]
          cyc 1  [ 4][ 5][ 6][ 7]
평면 b4   cyc 4  [ 0][x1][ 2][x3]      x = 이미 종단됐는데 끌려온 토큰
          cyc 5  [ 4][ 5][x6][ 7]
압축      cyc 8  (( 압축 오버헤드 ))
평면 b3   cyc 9  [ 0][ 2][ 4][ 5]      ← 압축 후: 생존 토큰만 앞으로
```

| 슬롯 | |
|---|---|
| 보라 | 살아있는 토큰을 처리 — **유효** |
| 회색 (취소선) | 이미 종단됐는데 끌려온 토큰 — **회수하지 못한 종단** |
| 빈칸 | 버블 |
| 주황 줄 | 압축 오버헤드 |

**유효 슬롯 수는 네 정책이 모두 같다.** 해야 할 일의 양은 정책이 바꾸지 못하고,
달라지는 것은 그걸 몇 사이클에 담느냐뿐이다 — 화면 상단에 그 숫자를 띄운다
(`test_useful_slots_are_identical_across_policies`).

16토큰 · 6평면 · 4레인 · 생존율 0.62 기준:

| | 사이클 | 레인 활용 | 유효 | 끌려온 종단 | 빈 레인 | BRAM 워드 |
|---|---:|---:|---:|---:|---:|---:|
| `none` | 24 | 40.6% | 39 | **57** | 0 | 24 |
| `batch` | 22 | 44.3% | 39 | 49 | 0 | 19 |
| `compaction` | 24 | 40.6% | 39 | **0** | 57 | **12** |
| `two_phase` | 15 | **65.0%** | 39 | 6 | 15 | 13 |

`compaction` 의 회색이 0 인 것이 정의 그대로이고
(`test_compaction_never_drags_terminated_tokens`), 대신 압축 줄이 평면마다 끼어들어
사이클은 `none` 과 같아진다. 그런데도 워드는 24 → 12 다. **사이클만 보면 무의미해
보이는 정책이 메모리 축에서는 압도적**이라는 것이 눈으로 보인다.

### ★ 그림이 본체를 설명한다는 보장

`build_trace()` 는 `apply()` 안의 식을 그대로 따라 슬롯을 채우고,
서버가 **매 요청마다** 트레이스 길이와 `apply().cycles` 를 대조한다.
어긋나면 그림을 그리지 않고 500 을 낸다.

```python
if len(cyc) != res.cycles:
    raise AssertionError(f"{name}: 트레이스 {len(cyc)} 사이클 != apply() {res.cycles} 사이클")
```

`matmul.py` 가 삼중 루프를 `A @ B` 와 대조하는 것과 같은 이유다 — 교보재가
본체와 갈라지면 화면이 설명하는 것은 본체가 아니게 된다.

### 그 밖의 그림

| | |
|---|---|
| **토큰 수명** | 토큰별로 몇 평면까지 읽히는지. 누르면 타임라인에서 그 토큰이 실린 슬롯이 전부 표시된다 |
| **BRAM 워드 읽기** | 평면별 워드 읽기. 평면을 누르면 아래 비교가 바뀐다 |
| **두 가지 배치** | 같은 생존 집합을 ① 있는 그대로 ② 앞으로 압축 — **진한 칸 수는 같은데** 읽는 워드가 다르다 |

### 손잡이 하나가 주제 전부다

「생존 토큰의 배치」(`clustering`) 는 **생존 토큰의 개수를 전혀 바꾸지 않는다.**
위치만 바꾼다. 그런데 결과가 갈린다 — 128토큰 · 8평면 · 생존율 0.55 ·
`lanes=32` · `word_tokens=32`:

| | 논리적 읽기 | `batch` 워드 절감 | `compaction` 워드 절감 |
|---|---|---|---|
| 흩어져 죽음 | 300 / 1024 (이론 **70.7%**) | **0.0%** | 56.2% |
| 뭉쳐서 죽음 | 300 / 1024 (**동일**) | **56.2%** | 56.2% |

`compaction` 만 배치와 무관하게 같은 값을 낸다 — 그것이 `src/schedule.py` 의

> ★ BRAM 워드 단위 읽기 절감을 실현하는 유일한 방법 ★

이 뜻하는 바다. 이론 70.7% 를 다 realize 하지는 못한다는 것(56.2%)도 함께 보인다.
남는 격차는 워드 알갱이 크기 자체의 하한이다.

### 파라미터는 실제 스펙까지 간다

슬라이더 범위를 `config/hardware.yaml` 의 값이 한가운데 오도록 잡았다.

| | 실제 | 슬라이더 |
|---|---:|---|
| `lanes` | 32 | 1 – 128 |
| `word_tokens` | 32 | 1 – 128 |
| `batch_size` | 32 | 1 – 256 |
| `two_phase_split` | 3 | 1 – 16 |
| `compaction_cost_cycles` | 2 | 0 – 16 |
| 비트평면 | 8 (INT8) | 2 – 16 |
| 문맥 길이 T | 512 목표 | 8 – 512 |

프리셋 **「실제 프로젝트 스펙」** 은 이 표를 베낀 것이 아니라 `hardware_defaults()`
가 `spec_from_config()` / `bram_from_config()` 로 **설정 파일에서 직접 읽는다.**
인터페이스 파일이 바뀌면 데모도 따라 움직인다
(`test_hardware_defaults_match_the_config_file`).

문맥 512 · 8평면 · 32레인이면 타임라인이 4,096 슬롯이라 그대로 그려진다
(`test_real_spec_renders_a_timeline`).

### 상황별 프리셋 6개

각 버튼이 **어떤 상황인지와 무엇이 보일지**를 함께 적어 둔다.

| 프리셋 | 무엇이 보이나 |
|---|---|
| 실제 프로젝트 스펙 | `config/hardware.yaml` 그대로 · 문맥 128토큰 |
| 한눈에 보기 (작게) | 16토큰 · 4레인 — 타임라인 전체가 한 화면에 |
| 종단이 **흩어져** 일어날 때 | batch 는 워드를 하나도 못 줄이고 compaction 만 줄인다 |
| 종단이 **뭉쳐서** 일어날 때 | batch 만으로도 compaction 과 같은 절감 |
| 종단이 **거의 없을** 때 | 압축이 비용만 남긴다 — compaction 80 cyc vs none 32 cyc |
| batch 가 **헛도는** 조건 | 토큰 없는 빈 사이클이 생긴다 (아래 결함) |

### 어느 정책이 유리한가 — 판정을 화면이 직접 낸다

요약 절에 **판정 상자**가 있다. 임계값 감각이 아니라 **그 설정에서 실제로 계산된
결과**로 판정한다 — "종단률 몇 % 면 무슨 상황" 같은 규칙은 `lanes` 나
`word_tokens` 가 바뀌면 바로 틀리기 때문이다.

| 상황 | 유리한 정책 | 왜 |
|---|---|---|
| 종단이 거의 없다 | `none` · `batch` | 회수할 것이 없는데 압축 비용만 낸다 |
| 종단이 **뭉쳐서** 일어난다 | `batch` | 재배치 없이도 워드를 건너뛴다. 압축 비용이 순손해 |
| 종단이 **흩어져** 일어난다 | `compaction` | ★ 워드 절감을 얻는 유일한 방법 |
| 흩어지는데 압축이 비싸다 | `two_phase` | 압축을 한 번만 내고 절감 대부분을 유지 |

판정 규칙은 다음 순서다 (전부 계산된 값으로만 본다).

```python
if   compaction 의 워드 절감 < 5%          -> no_gain          (회수할 게 없다)
elif compaction 절감 - batch 절감 <= 3%    -> clustered        (batch 로 충분)
elif two_phase 가 사이클이 더 적고
     워드 절감의 90% 이상을 유지            -> scattered_costly (two_phase)
else                                       -> scattered        (compaction)
```

**★ 한 정책을 '정답'으로 내놓지 않는다.** 사이클과 BRAM 워드는 서로 다른 축이고
실제로 자주 갈린다. 실제 스펙 · 생존율 0.62 · 흩어져 죽는 경우:

```
none:32cyc/32w   batch:32cyc/32w   compaction:30cyc/14w   two_phase:19cyc/17w
                 사이클 최소 = two_phase(19)   워드 최소 = compaction(14)
```

이때 화면은 **"두 축의 승자가 다르다"** 고 경고하고, Decode 가 메모리 병목이라
보통 워드 쪽을 본다는 것을 덧붙인다 (`test_verdict_reports_when_the_two_axes_disagree`).

### ⚠ 알려진 결함 — `batch` 의 부분 배치 과대계상

`src/schedule.py` 의 `cyc_per_plane_batch` 는 **한 번만** 계산해서 모든 배치에
똑같이 적용한다. 마지막 배치가 작을 때도 꽉 찬 배치와 같은 비용을 청구한다.

```
lanes=8, batch_size=64, n_tokens=200, 종단 전혀 없음
  마지막 배치 = 토큰 8개인데 ceil(64/8) = 8 사이클 청구
  -> 뒤쪽 사이클의 슬롯이 [None, ...]  ★ 토큰이 하나도 없는 사이클
  dense = 200,  batch = 256   (+28%)
```

프리셋 「★ batch 빈 사이클」 을 누르면 화면에서 그 줄에 표시가 붙는다.
`batch_size > lanes` 이고 나누어떨어지지 않을 때만 나타나며,
**기본 설정(`lanes=32, batch_size=32`)에서는 차이가 정확히 0** 이라 잠복해 있다.
실험 수치가 바뀌는 변경이라 고치지 않고
`test_batch_never_exceeds_dense_when_nothing_terminates` 에 `xfail(strict=True)`
로 고정해 두었다 — 고치면 XPASS 로 **실패**해서 마커를 지우라고 알려 준다.

### 주의 — 합성 입력이다

종단 패턴은 손잡이로 만든 것이지 실제 분포가 아니다. 실제 수치는
`experiments/exp1_termination_profile.py` 와 `exp4_schedule_policy.py` 가 낸다.
이 페이지는 **정책이 무엇을 하는지 이해하는 용도**이지 논문 수치를 내는 곳이 아니다.

## 이 프로젝트와의 관계

디코드 스텝의 `q · K^T` 도 결국 같은 모양이다 — **A 의 행이 하나뿐인 경우.**
스테퍼로 `A 행 i` 를 2 까지밖에 못 줄이는 것은 화면 제약일 뿐이고,
계산 쪽은 1행도 정상 처리한다 (`tests/test_visualization_example.py::test_single_row_query_is_allowed`).

```python
from utils.visualization_example import matmul

q   = [[5, -3, 7, 2]]                                   # 1 × d_head
K_T = [[200, 96], [32, 224], [176, 48], [16, 128]]      # d_head × T

matmul.breakdown(q, K_T, 0, 0)["terms"]   # 토큰 0 의 점수가 쌓이는 과정
```

여기서 한 걸음 더 나가면 이 저장소의 본론이 된다. 우리는 저 `terms` 를 **끝까지
돌리지 않는다** — K 를 비트평면으로 쪼개 상위 비트부터 처리하다가, 상한이
θ 아래로 떨어진 토큰은 남은 평면을 읽지 않고 버린다.
자세한 것은 [docs/background/attention_walkthrough.md](../../docs/background/attention_walkthrough.md) §4.

> 이 데모 자체는 **비트평면도 조기 종단도 다루지 않는다.** 그 앞 단계인
> "행렬 곱이 어떻게 계산되는가"까지만 설명한다.
