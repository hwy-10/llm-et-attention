## 1. 설계 파라미터

소프트웨어 골든모델(저장소 `llm-et-attention`)이 완성되어 **실측 근거가 생긴 값**과 **아직 어긋난 값**이 갈렸다. ⚠ 표시는 두 문서가 다른 값을 쓰고 있다는 뜻이며, `current_state.md` §11 의 미결정 항목과 같다.

**2026-08-28 전원 합의로 확정됨.** 골든모델 실측을 근거로 정했으며, 근거는 각 행의 비고에 있다.

| 기호 | 의미 | **확정값** | 근거 |
|---|---|---|---|
| `D` | head_dim (누산 깊이) | **64** | Llama 3.2 1B |
| `B` | K 원소 비트폭 | **8** | 평면 개수와 동일 |
| `N_MAX` | 최대 토큰 수 | **2048** | 2026-08-29 확정. 512 는 지는 구간이었다. BRAM 추가 0 (§4.2) |
| `K_TOP` | 상위 k 크기 | **16** | 품질 대가가 k=8 의 절반이다 (perplexity +5.8% vs +11.9%). 아래 표 |
| `LANES` | 토큰 병렬도 (Masked-Sum 유닛 수) | **32** | 구 `P`. 이름을 골든모델 `lanes` 로 통일 |
| `M0` | θ 확정 시점 (처리 평면 수) | **4** | 생존 곡선상 평면 4부터 종단이 시작된다 |
| `WORD_TOKENS` | 한 워드에 담기는 토큰 수 | **1** | §4.1.1. 워드 = 토큰 1개의 한 평면 = 64b |
| `N_PORTS` | BRAM 독립 포트 수 | **스윕 축** (16 권고) | §4.1.2. 이 값이 병목 위치를 정하고, 병목이 종단의 가치를 정한다 |
| `LATENCY_MODE` | 판정 지연 산출 | **`auto`** | §6.2.1. 상수가 아니라 `T` 의 함수다 (2026-08-29 확정) |
| `OUT_BUF` | 출력 상한 | **2048 (= `N_MAX`)** | §7.1.4. 별도 버퍼를 두지 않는다 |
| `IDX_BITS` | `score_idx` 폭 | **11** | `log2(N_MAX)`. `N_MAX` 와 반드시 함께 움직인다 |

전부 Verilog `parameter`로 노출한다. RTL에 상수 하드코딩 금지.

> **`N_PORTS` 와 `OUT_BUF` 는 2026-08-29 팀1 코드 병합에서 새로 확정/정정됐다.** 둘 다 8/28 시점에는 문서와 설정이 어긋나 있었고, 병합으로 골든모델이 완결되면서 드러났다. 각 절에 정정 경위를 남겼다.

**`K_TOP` 근거 — 실측 perplexity (2026-08-29 `exp8`, 보간 아님)**

`top-k 보존율`은 정확 모드에서 **어떤 k 를 써도 1.0000** 이라 판단 근거가 되지 못한다.
언어모델 품질을 직접 쟀다. **종단 로직을 어텐션에 넣고 전 층(16개)을 동시에 교체**한
상태의 wikitext perplexity 다.

```
    k   방식              ppl    full 대비   평균 생존   보간 추정(옛값)
    8   오라클 top-k    8.3313    +9.13%       7.9
    8   우리 (정확)     8.0996    +6.09%      10.0  ★      +11.9%
    8   우리 (m=0.70)   8.2564    +8.15%       8.5  ★
   16   오라클 top-k    7.9114    +3.63%      15.8
   16   우리 (정확)     7.8464    +2.78%      19.5  ★       +5.8%   <- 채택
   16   우리 (m=0.70)   7.8967    +3.43%      16.8  ★
   32   오라클 top-k    7.7491    +1.50%      31.0
   32   우리 (정확)     7.7123    +1.02%      37.3  ★       +2.7%
   32   우리 (m=0.70)   7.7288    +1.23%      32.8  ★

   full attention ppl = 7.6345     ★ = 오라클 하드 top-k 보다 좋다 (6/6)
```

**8 -> 16 이 knee 다.**

```
    8 -> 16    +6.09% -> +2.78%    품질 3.31%p 개선
   16 -> 32    +2.78% -> +1.02%    품질 1.76%p 개선
```

8->16 이 16->32 보다 **두 배 많이 얻는다.** 그 위로는 수익이 떨어진다.

**★ 6개 조합 전부 오라클 하드 top-k 보다 좋다.** 생존 집합이 top-k 의 **상위집합**이라
"버릴 수 없는 토큰" 이 함께 남기 때문이다. `docs/related_work.md` §0.1-(f).

> **옛 근거는 보간값이었다.** 하드 top-k 곡선에 생존 토큰 수를 로그 보간해 읽었는데
> (k=8 +11.9%, k=16 +5.8%, k=32 +2.7%), 상위집합 이득을 반영할 수 없어 **모든 k 에서
> 실제의 약 2배로 나쁘게** 나와 있었다. 우리에게 불리한 추정이었다.

> **`K_TOP` 은 2026-08-28 오전에 8 로 정했다가 오후에 16 으로 되돌렸다.** 오전 근거는
> 절감량뿐이었고 품질 쪽 근거가 없었다. 결과적으로 이 문서 초판의 값(16)으로 돌아왔으며,
> 이번에는 측정 근거가 있다.
>
> **`M0` 주의** — 골든모델 `two_phase_split` 기본값이 3 이므로 `config/hardware.yaml` 을 4 로 바꿔야 한다.

**★ `N_MAX` — 512 는 지는 구간이다**

설계 ③ 이 ② 를 이기는 손익분기가 **T ≈ 730** 이다 (추정 Fmax 165/185 MHz 기준).

```
    T     실효 speedup    판정
  512       0.9317       손해   <- 현재 N_MAX
  768       1.0091       이득   <- 교차점
 2048       1.1594       이득
```

그런데 **`WORD_TOKENS=1` 에서는 N_MAX 를 2048 로 늘려도 BRAM 이 늘지 않는다.** 폭(독립 포트 `LANES`=32개)이 제약이고 용량은 남기 때문이다.

```
  N_MAX    용량 기준   폭 기준   실제 필요   BRAM36 이용률
    512       8개       32개      32개         22%
   2048      29개       32개      32개         89%
```

**자원 추가 없이 손익분기 구간으로 들어갈 수 있다.** Llama 3.2 1B 가 128K 문맥을 지원하므로 T=2048 은 현실적인 운용점이다. → `current_state.md` §3.3 · §3.4

## 2. 알고리즘 정의

### 2.1 기본 전개

K는 부호 없는 8비트로 저장한다(비대칭 양자화, zero-point는 최종 단계에서 일괄 보정).

```
s_j = SUM(b=0..7) 2^b * P_b(j)

P_b(j) = SUM(i=0..D-1) q_i * K_ji^(b)      (K의 b비트가 1인 위치의 q 합)
```

처리 순서를 `m`으로 둔다. `m = 0`이 첫 번째로 처리하는 평면이며 비트 위치는 `b = 7 - m`이다.

```
S_m(j) = SUM(m'=0..m-1) 2^(7-m') * P_(7-m')(j)      (m개 평면 처리 후 확정분)
```

### 2.2 상한과 하한

q는 한 디코딩 스텝 동안 고정이므로 두 상수를 스텝당 1회 계산한다.

```
Qp = SUM of q_i where q_i > 0        (0 이상)
Qn = SUM of q_i where q_i < 0        (0 이하)
```

미처리 평면의 가중치 합은 `W_m = 2^(8-m) - 1` 이다.

```
상한  U_m(j) = S_m(j) + W_m * Qp
하한  L_m(j) = S_m(j) + W_m * Qn
```

`L_m(j) <= s_j <= U_m(j)` 가 항상 성립한다.

> **★ 성립 조건 두 가지 (2026-08-28 손 유도 + 반례 탐색으로 확인)**
>
> **① `0 <= K_stored < 2^B`**
> 벗어나면 비트평면이 K 를 대표하지 못해 상한식이 깨진다. 골든모델 `to_bitplanes()` 가
> uint16 으로 감싸며 조용히 잘랐던 자리이고, 지금은 입구에서 막는다.
> RTL 에서도 **쓰기 경로에서 범위를 보장**해야 한다.
>
> **② unsigned 정정 문구가 빠뜨린 것 — 평면 0 은 예외다**
> "signed 에서도 bound 를 세울 수 있다"는 정정은 맞지만, `m = 0` 에서는 별도 공식이 필요하다.
> ```
> m = 0    signed :  R_0 = -128*Qn + 127*Qp      unsigned :  R_0 = 255*Qp
>          unsigned 식을 signed 에 쓰면 Qp < |Qn| 인 q 에서 깨진다
>          반례  q = [1]x10 + [-128]x54  ->  참 최대 692,470  vs  255*Qp = 2,550
> m >= 1   남은 자리값이 전부 양수라 양쪽이 같은 형태
> ```
> **unsigned 의 이득은 평면 0 예외를 없애 8개 평면에 단일 공식을 쓰는 것**이다.

### 2.3 종단 조건

```
U_m(j) < theta   ->   토큰 j 종단
```

### 2.4 ★ theta 의 정의 — 설계상 가장 중요한 결정

`theta`를 "이미 확정된 점수 중 k번째"로 정의하면 문제가 생긴다. 평면 우선으로 처리할 경우 모든 토큰이 동시에 진행하므로, 어떤 토큰도 8평면을 끝내기 전까지 확정 점수가 하나도 없다. 즉 `theta`가 계속 미정이어서 **종단이 한 번도 일어나지 않는다.**

해결책은 확정 점수 대신 **하한값**을 쓰는 것이다.

```
theta = 현재 활성 토큰들의 L_m 값 중 K_TOP 번째로 큰 값
```

이 정의가 타당한 이유는 다음과 같다. `L_m` 이 `theta` 이상인 토큰이 최소 `K_TOP` 개 존재하고, 그 토큰들의 실제 점수는 각자의 하한 이상이므로 `theta` 이상이다. 따라서 `U_m(j) < theta` 인 토큰 j는 상위 `K_TOP` 안에 들 수 없다.

**손실 없는(exact) 판정이 유지되며, m = 1 시점부터 종단이 동작한다.**

근사 모드에서는 `theta` 에 여유값을 더한다.

```
theta_eff = theta + MARGIN        (MARGIN >= 0, 레지스터로 설정)
```

## 3. 고정소수점 비트폭

`q_i`는 INT8 부호 있는 정수(`-128 ~ 127`), `D = 64` 기준으로 유도한다.

| 신호 | 범위 | 폭 | 유도 |
|---|---|---|---|
| `q_i` | −128 ~ 127 | 8b signed | 입력 |
| `P_b` | −8,192 ~ 8,128 | **14b signed** | 64 × (−128) ~ 64 × 127 |
| `S_m` | −2,088,960 ~ 2,072,640 | **22b signed** | 255 × P_b 범위 |
| `Qp` | 0 ~ 8,128 | **13b unsigned** | 64 × 127 |
| `Qn` | −8,192 ~ 0 | **14b signed** | 64 × (−128) |
| `W_m * Qp` | 0 ~ 2,072,640 | **22b unsigned** | 255 × Qp |
| `W_m * Qn` | −2,088,960 ~ 0 | **22b signed** | 255 × Qn |
| `U_m`, `L_m` | −4,177,920 ~ 4,145,280 | **24b signed** | S_m + W_m·Qp/Qn |
| `theta` | U/L과 동일 | **24b signed** | 비교 대상과 폭 일치 |

`W_m` 은 상수 테이블(8엔트리)로 두거나 `(1 << (8-m)) - 1` 로 생성한다. `W_m * Qp` 는 22b × 13b 곱셈이지만 `W_m` 이 `2^n − 1` 꼴이므로 **시프트 후 뺄셈**으로 대체 가능하다.

```
W_m * X = (X << (8-m)) - X
```

곱셈기가 필요 없다.

### 3.1 골든모델과의 대조 (2026-08-28)

| 신호 | 이 문서 | 골든모델 | 상태 |
|---|---|---|---|
| `P_b` | 14b signed | `AdderTreeModel.output_bits = 14` | ✅ 일치 |
| `S_m` | 22b signed | `accumulator_bits(64) = 22` | ✅ 일치 |
| `Qp` / `Qn` | 13b unsigned / 14b signed | 표기 없음 (`bounds.py` 는 파이썬 정수) | — |
| `U_m`, `L_m`, `theta` | 24b signed | 표기 없음 | — |

**남은 두 가지가 RTL 설계 전에 정해져야 한다.**

**① `q_i` 의 하한이 −128 인가 −127 인가**

이 문서 §3 은 `q_i ∈ [−128, 127]` 을 전제로 폭을 유도했다. 골든모델은 **대칭 양자화라 −128 을 쓰지 않는다**(`quantize_query` 가 `[−127, 127]` 로 클립, `tests/test_quantize.py::test_query_quant_symmetric` 이 이를 강제).

```
이 문서 전제   Qn 최소 = -128 x 64 = -8,192   -> 14b signed
실제           Qn 최소 = -127 x 64 = -8,128   -> 14b signed  (같은 폭)
```

폭은 그대로이므로 **한 비트 여유가 생길 뿐 안전하다.** 다만 두 문서가 다른 전제를 쓰고 있으므로 하나로 맞출 것.

**② `theta` 의 "미확정" 상태를 회로에서 어떻게 표현할 것인가**

골든모델은 `theta` 를 부동소수로 다루고 미확정을 `-inf` 로 둔다(`threshold.py::kth_largest` 가 활성 토큰이 `K_TOP` 개 미만이면 `-inf` 반환). RTL 의 24b signed 정수에는 `-inf` 가 없다.

```
선택지 A : 24b 최솟값(-8,388,608)을 -inf 로 약속한다
           -> U_m 이 그보다 작을 수 없으므로 종단이 안 일어난다. 의미상 맞다
선택지 B : theta_valid 비트를 따로 둔다      ★ 채택
           -> valid=0 이면 종단 판정 자체를 건너뛴다. 명시적이라 안전하다
```

**B 로 확정한다.** A 는 "θ 가 매우 낮다"와 "θ 가 아직 없다"가 구분되지 않아, 디버깅 시 종단이 안 일어나는 원인을 추적할 수 없다.

```
term_ctrl 판정식
   if (theta_valid && active[j] && U_m(j) < theta_eff)  active[j] <= 0
```

`theta_valid` 는 `theta_engine` 이 세운다. `M0` 평면을 처리해 θ 를 처음 확정하는 시점에 1이 되고, 스텝이 끝나면 0으로 돌아간다. 골든모델의 `kth_largest()` 가 활성 토큰이 `K_TOP` 개 미만일 때 `-inf` 를 내는 경우도 `theta_valid = 0` 에 대응한다.

## 4. 메모리 구성

### 4.1 비트평면 배치

한 워드 = 토큰 하나의 한 평면 전체 = `D` 비트 = 64비트.

```
주소 매핑 (평면 우선)

   addr = m * N_MAX + j          (m: 처리 순서 0~7, j: 토큰 번호 0~N_MAX-1)

   +---------------- m=0 (b7) ----------------+
   | j=0 | j=1 | j=2 | ... | j=N_MAX-1        |
   +---------------- m=1 (b6) ----------------+
   | j=0 | j=1 | j=2 | ... | j=N_MAX-1        |
   ...
   +---------------- m=7 (b0) ----------------+
```

평면 단위 순차 처리 시 주소가 연속하므로 버스트 읽기에 유리하다. 종단된 토큰을 건너뛰면 주소가 불연속해지지만 BRAM은 임의 접근이므로 문제가 없다.

### 4.1.1 ★ 건너뛰기 단위(skip granularity) — `WORD_TOKENS = 1` 로 확정

위 주소 맵은 **논리적 배치**만 정한다. 실제 절감을 정하는 것은 **"한 번에 몇 개 토큰을 건너뛸 수 있는가"** 다.

```
WORD_TOKENS = 1    워드 = 토큰 1개의 평면 (64b)  ->  토큰 단위로 건너뛴다   ★ 채택
WORD_TOKENS = 32   워드 = 32토큰 x 64차원 (2048b) -> 32개 묶음으로만 건너뛴다
```

**대역폭은 어느 쪽이든 같다.** `LANES` 개 토큰을 한 사이클에 처리하려면 `LANES × 64` 비트가 필요하고, 이는 배치 방식과 무관하다. 갈리는 것은 **종단된 토큰을 실제로 건너뛸 수 있느냐**뿐이다.

**BRAM 개수도 거의 같다** (`LANES=32`, `N_MAX=512` 기준).

```
Xilinx BRAM36 = 36Kb, SDP 최대 폭 72b.  매 사이클 32x64 = 2,048b 필요

단위 = 1    워드 64b x 독립 포트 32개  ->  BRAM36 32개  (용량 기준으로는 8개면 충분)
단위 = 32   워드 2,048b x 포트 1개     ->  BRAM36 29개
```

즉 **자원 문제가 아니라 회로 복잡도 문제**다.

| | 단위 = 1 (채택) | 단위 = 32 |
|---|---|---|
| 주소 생성 | 독립 주소 32개 | 주소 1개 |
| 생존 토큰 모으기 | **주소만 바꾸면 된다 (공짜)** | 2,048b 에서 골라내는 크로스바 필요 |
| 실현 절감 (이론 27.9%) | 27.9% — **단 압축 정책일 때만** (아래 정정) | 압축 시 26.6% / 압축 없으면 3.8% |
| BRAM36 이용률 | 22% (8,192 / 36,864b) | 높음 |

**채택 이유** — 압축 회로가 필요 없다. 단위 1 에서는 생존 토큰 목록으로 주소를 만들면 BRAM 이 **이미 정렬된 데이터를 내주므로**, work-compaction 이 주소 생성에 흡수된다. 별도 크로스바가 사라진다. 대가는 BRAM 이용률 22% 인데, xc7z020 은 BRAM36 을 140개 갖고 있어 32개는 여유가 있다.

#### ★ 정정 (2026-08-29 병합) — 워드폭만으로는 정해지지 않는다

기존 표의 `batch` 열은 **실제로는 `two_phase` 값**이었다. `batch` 정책이 묶음 안의 죽은 토큰을 워드 회계에서 빼고 세어, 압축 수준의 절감을 공짜로 가져가고 있었다. 팀 1 이 `dragged` 배열로 고쳤다.

> **★ `exp4` 는 폐기하지 않는다 — 이 결정의 근거로 논문에 싣는다.**
>
> | 건너뛰기 단위 | batch | compaction | two_phase |
> |---|---|---|---|
> | **1** | **3.4% (12%)** | **27.9% (100%)** | 27.9% (100%) |
> | 8 | 3.7% (13%) | 27.6% (99%) | 12.3% (44%) |
> | 32 | 3.8% (14%) | 26.6% (95%) | 3.8% (14%) |
> | 64 | 3.8% (14%) | 24.4% (87%) | 1.5% (5%) |
>
> **읽는 법이 바뀐다.** `batch` 열은 워드폭을 아무리 줄여도 3.4~3.8% 로 평평하다 — 묶음(32)이 건너뛰기 단위를 정하므로 워드폭이 개입할 여지가 없다. 즉 **실현 절감은 워드폭과 스케줄 정책이 함께 정한다.** 둘 중 하나만 골라서는 안 된다.
>
> `WORD_TOKENS = 1` 채택은 유지되지만 **근거가 바뀐다.** "단위 32 면 14% 밖에 안 나온다" 가 아니라 **"압축 정책과 짝지어야 100% 가 나오고, 단위 1 이면 그 압축이 주소 생성에 흡수된다"** 이다.

#### ★★ `n_ports` 는 `word_tokens` 와 함께 움직여야 한다 (2026-08-29 발견) ★★

`WORD_TOKENS=1` 로 정하면서 `n_bram_ports` 는 2 로 남겨 두었다. 팀 1 의 메모리 사이클 모델을 붙이니 **메모리가 연산의 11배**가 됐다.

```
   memory_cycles = ceil(words_bram / n_ports)

   word_tokens=1,  n_ports=2    메모리 376,650  vs  연산 33,043   11배 병목
   word_tokens=1,  n_ports=32   메모리  23,761  vs  연산 33,043   연산 병목
   word_tokens=32, n_ports=2    메모리  12,801  vs  연산 33,043   연산 병목
```

조건은 이것 하나다.

```
   word_tokens x n_ports  >=  lanes
```

한 사이클에 `lanes` 개 토큰을 먹이려면 `lanes × D` 비트가 필요하다. 워드가 좁아진 만큼 포트가 늘어야 대역폭이 유지된다. 위 §4.1.1 이 "독립 포트 32개 → BRAM36 32개" 로 계산해 놓고 `hardware.yaml` 은 `n_bram_ports: 2` 로 두어 **문서와 설정이 어긋나 있었다.**

**`n_bram_ports: 2 → 32` 로 고쳤다.** 테스트 4개의 전제도 하드코딩된 설정값에서 이 부등식으로 일반화했다.

### 4.1.2 ★★ 그런데 포트를 늘리면 종단의 값어치가 사라진다 ★★

`2 → 32` 정정은 "메모리가 연산의 11배" 인 명백한 불균형을 없앤 것이라 맞다. **다만 32 까지 갈 필요는 없었다.**

```
   total = max(compute, memory)          memory = ceil(words_bram / n_ports)
```

조기 종단이 줄이는 것은 **메모리**다. 포트를 늘리면 메모리 시간이 줄어 어느 지점에서 연산 아래로 내려가고, 그 순간부터 `max()` 가 연산을 집으므로 **메모리를 아무리 아껴도 시간이 안 준다.**

`exp7` 이 이 교차점을 찾는다 (정확 모드, ② 대비 비율. 1.0 미만이면 이득).

```
   포트 |   N=256          N=512          N=1024
        | 시간  읽기 병목 | 시간  읽기 병목 | 시간  읽기 병목
      2 | .886 .886 메모리| .787 .786 메모리| .753 .753 메모리
     16 | .908 .886 메모리| .793 .786 메모리| .755 .753 메모리
     24 |1.068 .886  연산 | .835 .786  연산 | .766 .753 메모리
     32 |1.299 .886  연산 |1.021 .786  연산 | .878 .753  연산
     64 |1.299 .886  연산 |1.021 .786  연산 | .878 .753  연산
```

**읽기 비율은 포트와 무관하다** — 종단 로직이 같으니 당연하다. **시간 비율만 움직인다.**

```
   교차점 (병목이 메모리 → 연산)     N=256: 24    N=512: 24    N=1024: 32
```

**문맥이 길수록 교차점이 올라간다.** 메모리 병목 구간이 넓어지므로 종단이 더 오래 값어치를 한다. 이것이 이 설계가 긴 문맥을 노리는 이유의 정량적 근거다.

#### 채택: `N_PORTS` 를 고정값이 아니라 **스윕 축**으로 둔다

```
   n_ports=16   절대 시간 느림   종단 이득 21%   ← 종단이 시간을 산다
   n_ports=32   절대 시간 빠름   종단 이득  0%   ← 절감이 전력으로만 남는다
```

둘 다 가질 수 없다. 하나를 고르는 대신 **"병목이 넘어가는 지점" 자체를 결과로 보고한다.** 프로젝트가 스스로를 *"FPGA 이득–오버헤드 특성화"* 로 규정했으므로 이 교차점이 곧 기여다.

> **RTL 은 `N_PORTS = 16` 으로 만든다.** 종단이 시간을 사는 영역이어야 제안의 논지가 성립한다. 32 는 비교군으로 함께 합성해 "포트를 늘리면 종단이 무의미해진다" 를 실측으로 보인다.

**골든모델에 반영할 것** *(전부 반영 완료)*

- `config/hardware.yaml` 의 `word_tokens: 32` → **1**
- `word_bits: 32` → **64** (워드 하나가 토큰 1개의 평면 = `D` 비트)
- `n_bram_ports: 2` → **32** ★ 위 부등식
- `bram36: 16` → **32** (폭 기준. 둘 다 `source: estimate` 이므로 Vivado 실측으로 교체)

> **`LANES` 를 줄이면 BRAM 도 준다.** `LANES=8` 이면 512b/사이클이라 BRAM36 8개로 떨어져 용량과 딱 맞는다. 부등식도 `1 × 8 >= 8` 로 만족한다. 대신 사이클이 4배 늘어난다. Phase 1 합성 결과를 보고 재조정할 여지가 있다.

### 4.2 용량

**BRAM36 32개는 대역폭 때문에 잡은 것이지 용량 때문이 아니다.** 그래서 `N_MAX` 를 늘려도 BRAM 이 늘지 않는다 — 놀고 있던 자리를 쓸 뿐이다.

```
   N_MAX    비트평면 저장    이용률    idx_bits   BRAM 추가
     512       262,144 b      22%         9          0
    1024       524,288 b      44%        10          0
    2048     1,048,576 b      89%        11          0     ★ 채택
    4096     2,097,152 b     178%        12         25
```

`(BRAM36 32개 = 1,179,648 b)`

**2026-08-29 `N_MAX = 2048` 확정.** 512 는 손익분기 미달 구간이었고(§1.1), 늘리는 데 자원이 들지 않는다.

> ⚠ **`N_MAX` 와 `IDX_BITS` 는 반드시 함께 움직인다.** `score_idx` 가 토큰 번호를 담아야 하므로 `2^IDX_BITS ≥ N_MAX` 다. 골든모델은 `output_stage` 가 폭 초과를 **예외로 막으므로** 한쪽만 고치면 바로 걸린다. `tests/test_output_stage.py::test_config_wiring_is_connected` 가 `config.seq_len` 에서 유도해 셋을 대조한다.

### 4.3 쓰기 경로

새 토큰의 K 벡터(64개 × 8비트)를 저장하려면 8개 평면에 1비트씩 분산 기록해야 한다.

```
입력  : K[0..63], 각 8비트
출력  : 8개 워드 (평면당 64비트)
```

전치 버퍼(transpose buffer)를 두어 64×8 비트를 받아 8×64 비트로 재배열한 뒤 8사이클에 기록한다. 디코딩 스텝당 1회만 발생하므로 읽기 대비 비중이 작다.

## 5. 스케줄링 방식

### 5.1 세 가지 선택지

| 방식 | 처리 순서 | 장점 | 단점 |
|---|---|---|---|
| A. 평면 우선 | 모든 토큰의 m=0 → 모든 토큰의 m=1 → … | 주소 연속, theta를 전역 하한으로 산출 가능 | theta 산출을 위한 하한 정렬 필요 |
| B. 토큰 우선 | 토큰 0의 m=0~7 → 토큰 1의 m=0~7 → … | 점수가 즉시 확정되어 theta 갱신이 단순 | 종단 절감이 해당 토큰 내부로 한정, 주소 불연속 |
| C. 2단계 | 1단계: 전 토큰 m=0~M0 스캔 → 2단계: 생존 토큰만 나머지 | 1단계 비용이 예측 가능, theta를 한 번만 계산 | 2단계 진입 시 재시작 오버헤드 |

### 5.2 채택안

**A(평면 우선) 를 기본으로 하고, theta 산출 방식으로 C의 아이디어를 흡수한다.**

```
m = 0 .. M0-1   : 종단 없이 전 토큰 스캔 (theta 미확정)
m = M0          : 활성 토큰의 L_m 중 K_TOP 번째 값을 theta 로 확정
m = M0 .. 7     : 매 평면마다 U_m < theta 판정, 종단
```

`M0` 를 키우면 theta 가 정확해져 종단률이 오르지만 1단계 비용이 커진다. `M0` 는 스윕 대상 파라미터다.

Phase 3(§9)에서는 매 평면마다 theta 를 갱신하는 방식으로 확장한다.

### 5.3 ★ 사이클 모델 — 연산축과 메모리축을 따로 센다 (2026-08-29 팀1)

지금까지 "설계 ②가 ①보다 8배 느리다" 고 써 온 값은 **연산 사이클만 센 것**이었다. 기준선(①)도 K 를 전부 읽어야 하므로 메모리 시간이 있다. 팀 1 이 이 축을 골든모델에 넣었다.

```
   memory_cycles = ceil(words_bram / n_ports)

   total_cycles  = max(compute, memory)     mem_overlap = true   (읽기와 연산이 겹친다)
                 = compute + memory         mem_overlap = false  (직렬)
```

병합 설정(`WORD_TOKENS=1`, `N_PORTS=32`, `LANES=32`, `K_TOP=16`, T=512)에서:

```
   설계        연산      메모리     합계(overlap)
   baseline    4,305    32,760     32,760      <- ① 도 메모리 병목이다
   seq        34,440    32,760     34,440
   exact      34,516    25,216     34,516

   연산축   ②/① = 8.00
   메모리축 ②/① = 1.05       ★
```

**격차가 8배에서 1.05배로 줄어든다.** 포트를 32개로 늘리면 기준선의 읽기 시간도 함께 줄기 때문이다. 즉 **설계 ②는 기준선과 거의 같은 시간에 끝난다.** "비트평면 순차 처리는 8배 느리다" 는 우려가 이 설정에서는 사실상 해소된다.

> `mem_overlap` 은 현재 `true` 로 두었으나 **RTL 실측으로 확정해야 한다.** `false` 면 합계가 `compute + memory` 라 두 배 가까이 늘어난다. → `current_state.md` §11

### 6.2 `masked_sum`

```
입력  : plane_word [D-1:0]        (BRAM에서 읽은 64비트)
        q_vec      [D-1:0][7:0]   (레지스터 파일, 스텝 동안 고정)
출력  : p_b        [13:0] signed

동작  : for i in 0..D-1:  term_i = plane_word[i] ? q_vec[i] : 0
        p_b = SUM(term_i)
```

- 마스킹: 비트당 8개 AND 게이트
- 가산 트리: 64입력, 깊이 6단
- **파이프라인 3단 권장** (2단씩 묶어 레지스터 삽입)
- 자원 추정: 유닛당 600~800 LUT (합성 결과로 확정)
- **DSP 사용 안 함**

### 6.2.1 ★★ 판정 지연은 상수가 아니다 — 문맥 길이에 의존한다 ★★

평면 `m` 의 종단 판정은 평면 `m` 의 가산 트리가 끝나야 나온다. 그 시점에 평면 `m+1` 의 읽기 요청이 이미 나갔으면 그만큼 절감이 줄어든다. 이 값을 작게 잡으면 **읽기 절감이 과대평가된다.**

문제는 **파이프라인 지연(사이클)과 판정 지연(평면)의 단위가 다르다**는 것이다. 한 평면을 처리하는 데 `ceil(T / LANES)` 사이클이 걸리므로, 환산식은 이렇다.

```
   판정 지연(평면) = ceil( 파이프라인 사이클 / ceil(T / LANES) )

   파이프라인 사이클 = 가산 트리 6단 + 마스킹 1 + 비교기 1 = 8
```

`LANES = 32` 기준으로 계산하면 **T 에 따라 크게 달라진다.**

```
    T    평면당 사이클   판정 지연(평면)
   32          1              8      <- 지연이 전 평면. 종단 이득이 0 이 된다
   64          2              4
  128          4              2
  256          8              1
  512         16              1
 2048         64              1
```

**실제 절감에 미치는 영향** (`WORD_TOKENS=1`, `K_TOP=8`, 정확 모드 실측)

```
    T    지연=1 가정   실제 지연   실제 절감    차이
  128       20.9%          2       10.7%    -10.2%p   <- 절반으로 준다
  256       25.5%          1       25.5%     +0.0%p
  512       27.9%          1       27.9%     +0.0%p
```

**골든모델의 `decision_latency_planes: 1` 은 `T ≥ 256` 에서만 맞다.** 짧은 문맥에서는 절감을 최대 2배 과대평가한다.

#### ★ 2026-08-29 확정 — `decision_latency_mode: "auto"`

디코드 루프 안에서도 스텝마다 다르다. 스텝 `s` 의 활성 토큰은 `warmup + s` 이므로 **루프 초반에는 지연이 8평면, 후반에는 1평면**이다. 루프 전체에 고정값 하나를 쓰면 초반 스텝의 절감을 과대평가한다.

```
   fixed   스텝마다 무조건 1        T >= 256 에서만 맞다.  기존 수치 재현용
   auto    스텝마다 T 로부터 계산   ★ 채택 — 물리적으로 맞다
```

**`auto` 로 바꾼 대가** (정확 모드, `K_TOP=16`)

```
    T     fixed      auto      차이     평균 지연(평면)
  128     14.9%      4.0%    -10.8%p       3.06
  256     19.4%     11.4%     -8.0%p       2.32
  512     23.3%     21.4%     -1.9%p       1.61
 1024     22.4%     20.5%     -1.9%p       1.61
```

**짧은 문맥에서 절감이 거의 사라진다.** 이것이 사실이며, 부풀린 숫자를 버리고 방어 가능한 숫자를 쓴다. 동시에 **"이 설계는 긴 문맥용" 이라는 논지를 정량적으로 뒷받침한다** — `T=128` 에서 4%, `T=512` 에서 21.4%.

> `auto` 는 설계 선택이 아니라 **사실**이다. 파이프라인 깊이 8은 고정이고, 그것이 몇 평면인지는 `T` 가 정한다. 회로가 고르는 값이 아니다.
>
> mock RTL 수치도 함께 재생성했다 — crosscheck 가 `T=128, 256` 에서만 어긋나며 이 변경을 정확히 잡아냈다.

**RTL 설계 지침** — `decision_latency_planes` 를 `parameter` 로 두지 말고, `n_token` 과 `LANES` 로부터 런타임에 계산할 것. 상수로 박으면 짧은 문맥에서 **무손실이 깨진다**(판정이 늦게 반영되는 것을 회로가 모르므로).

**자원 추정** — 이 문서의 600~800 LUT 는 골든모델의 `est_lut_total = 880` 과 어긋난다. 다만 골든모델의 `lut_per_fa = 1.0` 은 근거 없는 가정이므로 **양쪽 다 Vivado 실측으로 교체될 값**이다.

### 6.3 `bound_calc`

```
W_m * X = (X << (8-m)) - X        (곱셈기 불필요)

U_m = S_m + ((Qp << (8-m)) - Qp)
L_m = S_m + ((Qn << (8-m)) - Qn)
```

`(8-m)` 은 0~8 범위이므로 배럴 시프터 1개로 처리한다.

### 6.4 `term_ctrl`

```
상태  : active [N_MAX-1:0]        1비트/토큰

매 평면 m, 토큰 j 에 대해:
   if (active[j] && U_m(j) < theta_eff)  active[j] <= 0
```

`active[j] = 0` 인 토큰은 **`kv_plane_mem` 의 읽기 요청 자체를 발생시키지 않는다.** 이것이 성립하지 않으면 메모리 절감 효과가 사라지므로, 검증 시 읽기 요청 카운터로 반드시 확인한다.

**골든모델 대응** — `src/terminator.py` 의 `TerminationController.process_plane()` 한 번이 이 블록의 한 평면에 대응한다. 반환하는 `PlaneDecision` 이 그 평면의 `read_mask` · `lower` · `upper` · `theta` · `killed` 를 전부 담으므로 **RTL 파형과 평면 단위로 대조할 수 있다.** → §10.1

### 6.5 `theta_engine`

| Phase | 방식 | 구현 |
|---|---|---|
| 1 | 고정값 | 레지스터 1개 |
| 2 | m=M0 시점에 1회 산출 | L_m 값들의 K_TOP번째 → 부분 정렬 |
| 3 | 매 평면 갱신 | 위 구조 재사용 + 파이프라인 |

Phase 2/3의 부분 정렬은 bitonic 부분 정렬망 또는 K_TOP 크기의 삽입형 레지스터 배열로 구현한다. `K_TOP`이 작으면(16 이하) 후자가 유리하다.

## 7. 상태 기계 (`top_ctrl`)

```
IDLE
  |  start
  v
LOAD_Q        q 벡터 수신, Qp/Qn 산출
  |
  v
WRITE_K       새 토큰 K를 평면 메모리에 기록 (전치)
  |
  v
INIT          active <= 전체 1,  m <= 0,  S <= 0
  |
  v
SCAN_PLANE  <-----------------+     active 토큰에 대해 평면 m 읽기
  |                           |     -> masked_sum -> shift_acc
  v                           |
BOUND_CHECK                   |     m >= M0 이면 U_m < theta 판정
  |                           |     active 갱신
  |                           |
  +-- m < 7 --> m <= m+1 -----+
  |
  | m == 7
  v
OUTPUT        최종 점수 + zero-point 보정 출력
  |
  v
IDLE
```

`m == M0` 진입 시 `theta_engine` 을 1회 기동한다(Phase 2 기준).

## 7.1 ★ 출력 경로 (`OUTPUT` 단계) — 팀 2 소유

2026-08-28 확정. 상태 기계의 마지막 단계이며 **생존 집합을 정하는 것이 `term_ctrl`(팀 2 블록)** 이므로 이 단계도 팀 2 가 맡는다.

### 7.1.1 무엇을 내보내는가 — 생존 집합 전부

```
   (a) 생존 집합 전부      ★ 채택      개수 가변,  perplexity +5.8%
   (b) 정확히 K_TOP 개                고정 개수,  perplexity +12.2%,  최종 정렬 회로 필요
```

정확 모드의 생존 집합은 **top-k 의 상위집합**이다. 상한이 θ 를 못 넘는 것만 버리므로
버릴 수 없는 토큰이 함께 남고, 그래서 품질이 하드 top-k 보다 낫다. 자르면 그 이득을
버리게 된다. → `current_state.md` §3.7

### 7.1.2 출력 형식

```
   생존 토큰마다 (인덱스, 점수) 한 쌍을 스트림으로 낸다

     score_idx   [log2(N_MAX)-1 : 0]   토큰 번호
     score_data  [23 : 0]  signed      zero-point 보정 후 정수 점수
     score_valid                       1이면 이번 사이클 값이 유효
     score_last                        마지막 토큰에서 1 (개수가 가변이므로 필요)
```

`score_last` 를 새로 넣는다. **개수가 가변이라 다운스트림이 끝을 알 방법이 필요하다.**

### 7.1.3 zero-point 보정은 여기서 한 번만

```
   s_real = scale_q · ( S_8(j) − Σ_i q_st_i · z_i ) / sqrt(d)
                                └─ 스텝당 상수 ─┘
```

보정항은 **모든 토큰에 동일한 상수**라 순위에 영향이 없다. 그래서 `term_ctrl` 은
정수 점수만 보고 판정하고, 보정은 출력 단계에서 한 번만 뺀다. 24b 감산기 하나면 된다.
(`tests/test_quantize.py::test_zero_point_correction_is_rank_invariant` 가 순위 불변을 강제)

`scale_q` 와 `/sqrt(d)` 는 실수 배율이라 **하드웨어 밖으로 넘긴다.** 정수 점수와
`zp_correction` 만 내보내면 소프트웨어가 복원할 수 있다.

### 7.1.4 ★ 출력 버퍼 — 두지 않는다 (2026-08-29 정정)

**8/28 사양은 `OUT_BUF = 2 × K_TOP = 32` 였다. 틀렸다.**

근거였던 "실측 최대 31, 2×K_TOP 초과 0회" 는 **시드 하나만 본 값**이었다. `src/output_stage.py` 를 실제로 구현해 다시 재니 이렇게 나온다.

```
   시드        exact/margin=0        approx/margin=0.5
              평균  p99  최대       평균  p99  최대
        0     20.7   29   31       18.3   23   24
        1     20.8   29   31       18.3   23   24
        7     20.8   28   30       18.2   23   25
 20260829     20.7   29   34  ★    18.2   23   26
    31337     21.2   29   31       18.4   24   29

   관측 최대   exact 34,  approx 29        ->  32 로는 부족하다
```

32 로 두면 그 스텝은 **무손실이 아니다.**

**그런데 애초에 버퍼가 필요 없다.**

내보낼 `(토큰 번호, 확정 점수)` 는 둘 다 데이터패스에 **이미 있다.**

```
   S_m 레지스터 파일   N_MAX x 22b    평면 루프 내내 T개를 들고 있어야 한다 (필수)
   active 마스크       N_MAX x  1b    term_ctrl 이 종단 판정에 쓰는 그 비트
```

`OUTPUT` 은 `active` 를 훑으며 `S_m` 을 읽어 내보내면 된다. **새 저장소가 0 이다.**

```
                     추가 저장   추가 회로              무손실
   2xK_TOP 버퍼안     +1,056b   부분정렬(상한 상위 32)   깨진다
   S_m 직접 스캔          +0b   스캔 카운터 + 비교기     보장
```

**버퍼를 따로 두는 쪽이 자원을 더 쓰면서 무손실을 깬다.** 8/28 에 "가드의 대칭 버전을 재사용한다"고 쓴 부분정렬 회로도 함께 사라진다.

**채택: 별도 출력 버퍼 없음. `OUT_BUF` 는 "자르는 지점" 이 아니라 넘으면 안 되는 상한(= `N_MAX` = 512)이다.**

```
   config/hardware.yaml   output.out_buf: 512      # = N_MAX
```

골든모델은 이 값을 넘으면 `CNT_TRUNC` 를 올린다. 자르기 경로는 코드에 남겨 두되(버퍼를 줄이는 변형을 재려면 필요하다) **채택 설정에서는 절대 타지 않으며, `CNT_TRUNC == 0` 이 유지되는지가 검증 항목이 된다.**

> `N_MAX` 를 2048 로 늘리면 `S_m` 이 2048×22b = 45Kb (BRAM36 2개), `idx_bits` 는 9 → **11** 이다. `output_stage` 가 폭 초과를 예외로 막으므로 `idx_bits` 를 안 고치면 바로 걸린다.

### 7.1.5 검증 항목 — `tests/test_output_stage.py` (24개) 로 구현 완료

- [x] `score_last` 가 정확히 마지막 유효 토큰에서만 1 인가
- [x] 생존 수가 `OUT_BUF` 를 넘는 스텝에서 `CNT_TRUNC` 가 증가하는가
- [x] 잘라낸 뒤에도 참 top-`K_TOP` 이 남는가 — **실측이 아니라 성질로 증명된다**
- [x] zero-point 보정 전후 순위가 같은가 (골든모델 `fold_and_quantize_query` 와 대조)
- [x] 채택 설정(`out_buf = N_MAX`)에서 자르기가 원리적으로 불가능한가
- [x] `idx_bits` / `score_data_bits` 초과를 조용히 넘기지 않는가

**세 번째 항목이 증명이 되는 이유.** 출력 시점에는 평면을 다 처리했으므로 `m = n` 이고 잔여 계수가 0 이다.

```
   U_m = S_m + (2^(n-m) - 1) · Q+        m = n  ->  U_n = S_n
```

즉 **출력 시점에는 상한 = 확정 점수**다. 7.1.4 의 "상한 상위로 자른다" 는 "점수 상위로 자른다" 와 같은 말이고, `OUT_BUF ≥ K_TOP` 이기만 하면 참 top-k 는 절대 잘리지 않는다. 실측 통계가 필요 없다.

> 다시 뽑아야 한다. 또 `M0`·`K_TOP`·`P` 를 §1 에서 확정해야 Phase 1 로 넘어갈 수 있다.

Phase 3까지 완료하면 "정확도 손실 없이 읽기 N% 감소"라는 완결된 결과가 나온다. Phase 4 이후는 확장이다.

## 10. 검증 계획

### 10.1 골든 벡터

PyTorch 골든모델이 다음 형식으로 출력한다.

```
q.hex          : D개 × 8비트
k.hex          : N × D개 × 8비트
score_ref.hex  : N개 × 24비트 (signed, 정확 계산값)
term_ref.txt   : 토큰별 종단 평면 번호 (기대값)
```

#### ★ 평면별 중간값 대조 — `TerminationController` (2026-08-29 추가)

위 네 파일은 **스텝의 최종 결과**만 담는다. 파형이 틀렸을 때 **어느 평면에서** 갈라졌는지
알 수 없다. 팀원이 만든 `terminator_v2` 를 채택하면서 평면별 관측 경로가 생겼다.

```python
from src.terminator import TerminationController

ctrl = TerminationController(bounds, policy, n_tokens, decision_latency=1)
while not ctrl.done:
    dec = ctrl.process_plane(P[ctrl.next_plane])    # PlaneDecision
    #   dec.read_mask    이 평면에서 실제로 읽는 토큰
    #   dec.lower/upper  구간
    #   dec.theta        그 시점의 기준선
    #   dec.killed       이 평면에서 죽인 토큰
result = ctrl.finish()
```

**RTL 파형과 평면 단위로 맞출 수 있다.** `SCAN_PLANE` → `BOUND_CHECK` 한 바퀴가
`process_plane()` 한 번에 대응한다.

배치 경로(`run_step`)와 결과가 같음을 `tests/test_terminator.py::test_streaming_equals_batch`
가 40회 무작위로 고정한다. 한쪽만 고치면 거기서 걸린다.

### 10.2 검증 항목

| 항목 | 방법 |

- `N_MAX` 확장 여부 — 손익분기가 문맥 길이에 강하게 의존한다 (§9)

**margin 정규화 근거** (top-8, seq_len=256 실측)

```
margin   relative_width          relative_gap
         절감      보존율        절감      보존율
 0.00    22.87%   1.0000        22.87%   1.0000
 0.80    46.42%   1.0000        28.78%   0.9665
 1.00    59.91%   0.5117        29.93%   0.9621
```

`relative_gap` 은 margin=1.0 에서 θ 가 1등 하한까지만 올라가므로 **구조적으로 포화**한다(29.9%). 절감–정확도 곡선을 얻는 것이 목적인데 곡선이 그려지지 않는다. `relative_width` 는 무손실 구간(0~0.8)과 붕괴 지점(1.0)이 뚜렷해 knee 가 보인다.

> **골든모델에 반영할 것** — `src/threshold.py` 독스트링의 *"relative_width 는 잘 안 듣는다. 참고용으로만 둔다"* 는 **실측과 반대이므로 삭제**한다. 또 knee 가 0.8~1.0 사이에 있으므로 `sweeps.yaml` 의 margin 스윕을 그 구간에서 촘촘히 할 것.
